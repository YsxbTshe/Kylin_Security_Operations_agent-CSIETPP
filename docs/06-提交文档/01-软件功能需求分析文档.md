# 软件功能需求分析文档

## 1. 引言

### 1.1 编写背景

传统运维依赖脚本、人工规则和监控平台，门槛高、效率低，且容易因误删、误改配置、误操作导致系统故障。大语言模型（LLM）为自然语言驱动的智能运维带来可能，但同时引入幻觉、越权、Prompt 注入、指令偏移和执行不可控等新风险。

官方赛题要求构建一个在麒麟操作系统环境中完成真实运维任务的智能体，使其成为**自然语言与 OS 运维操作之间的安全桥梁**：通过 MCP 协议调用系统工具、采集状态、分析问题、执行任务，同时以安全护栏机制约束 AI 推理不确定性带来的误操作。项目主线为两个关键词：

> **智能化运维能力 + 安全可控执行机制**

### 1.2 系统目标

构建"平台侧智能体大脑 + 节点侧受控执行 Agent"的两级架构，达成以下目标：

| 目标 | 说明 | 对应题面要求 |
|---|---|---|
| G1 环境深度感知 | 自动调用 lsof / netstat(ss) / journalctl 等获取进程、网络、日志实时上下文，形成结构化诊断证据 | 功能要求 (1) |
| G2 运维插件化 | 底层运维动作封装为标准 MCP Tools，可注册、可发现、可扩展、可审计 | 功能要求 (1) |
| G3 安全意图校验 | 风险识别规则库 + LLM 指令二次过滤 + 高危参数识别，独立于 LLM 的同步校验 | 功能要求 (2) |
| G4 最小权限执行 | Agent 以受限账户运行，进程内不使用 root；写操作经 root 特权助手 privhelper 的固定映射表下沉执行；宿主机侧禁止通用 shell；脚本能力仅存在于隔离沙箱 | 功能要求 (2) |
| G5 抗注入与溯源 | 识别提示词注入；完整记录"接收指令→感知环境→推理决策→安全校验→执行结果"闭环日志 | 功能要求 (3) |
| G6 确定性与根因分析 | 严禁未授权修改关键配置；综合多源数据分析故障并提出自动化处置方案 | 功能要求 (4) |

效率参考锚点（官方题面给出的行业量化参考，作为本系统设计目标）：故障排查时长 45 分钟 → 18 分钟；故障定位准确率 92%；RAG 辅助根因命中率 70%+。

### 1.3 术语与定义

| 术语 | 定义 |
|---|---|
| Control Plane | 平台侧控制平面（Spring Boot 后端），承载 Agent 运行时、策略、审批、审计、RAG 与 IAM |
| Agent Run | 控制面的一次受控 Agent 运行（表 `agent_run`），由自然语言目标 + 执行模式 + 授权范围（grant）+ 预算构成 |
| AgentRoundExecutor | Agent 运行时的 ReAct 主循环：模型原生 function-calling → 门禁 → 工具执行 → 观察回填，逐轮推进 |
| DispatchGate | 工具下发前的确定性门禁链（授权 / 策略 / 意图 / 风险 / 执行模式 / ABAC / 安全姿态 / 审批），见 `DispatchGate.java` |
| Node Executor Runtime | 节点侧受控执行 Agent（Go 实现，`kylin-node-executor.service`），只消费经门禁与签名令牌校验的调用 |
| MCP | Model Context Protocol，基于 JSON-RPC 2.0 的标准工具协议；本系统节点侧实现 `initialize` / `tools/list` / `tools/call` 三个方法 |
| SubmitInvocation | 平台经 gRPC ControlStream 下发给节点的结构化受控调用（proto v2 消息），携带风险、审批令牌、资源锁、幂等与 traceparent |
| Policy Engine | 平台侧风险策略引擎，输出 R0–R5 风险等级与拦截/审批决策 |
| IntentAlignmentGuard | 动态意图对齐校验器，校验工具调用与用户原始意图的一致性 |
| ABAC | 资源级授权：按「主体 × 资源 × 动作」判定，工具维度（`agent-tool`）与主机维度（`HOST`）串联，default-deny |
| privhelper | 节点侧 root 特权助手进程（unix socket + SO_PEERCRED + 固定操作映射表 + 独立验签），承接全部写操作 |
| Kylin Native Guard | 麒麟原生安全姿态探测（KYSEC / SELinux / auditd / security-switch）与风险联动 |
| R0–R5 | 系统内部风险六级，对外映射官方四级：只读（R0/R1）、可逆（R2）、不可逆（R3/R4，需审批）、关键（R5，直接拦截） |
| 审计事件（Audit Event） | 控制面 `agent_run_event` 中的最小审计单元，以 SM3 哈希链防篡改 |

### 1.4 文档约定

- 功能需求编号 `FR-xyz`：x 对应官方四条功能要求序号，yz 为顺序号；非功能需求编号 `NFR-Xn`：X∈{S 安全, P 性能, R 可靠, A 审计, M 维护}；
- 优先级：P0=比赛演示主链路必需；P1=作品完整性必需；P2=增强项；
- 每条功能需求均给出"系统实现映射"，与《软件功能设计文档》对应章节互为追踪（见 3.5 节追踪矩阵）；
- 关键词"必须 / 禁止"表示强制要求，"支持"表示本版功能范围内的能力。

## 2. 用户与角色

系统内置 RBAC 权限模型（组织 / 角色 / 权限三级），业务角色与系统角色映射如下：

| 业务角色 | 系统 RBAC 角色 | 主要职责 | 关键权限边界 |
|---|---|---|---|
| 平台管理员 | `platform_admin` | 全局用户、组织、角色、模型配置、证书生命周期管理 | 唯一可执行证书吊销/轮换、策略 DSL 发布 |
| 组织管理员 | `org_admin` | 组织内用户管理与安全运维 | 仅限本组织资源（组织级隔离） |
| 运维操作员 | `security_operator` | 发起对话运维 / Agent 任务，处置告警与安全事件，查看审计 | 可发起 R3/R4 任务但**发起人不可自批** |
| 审批人 | 持 `agent:approve` 的 `platform_admin` / `org_admin` / `security_operator` | 在审批中心复核 R3/R4 不可逆动作 | 发起人不可自批；审批令牌一次性消费并由节点侧独立验签 |
| 评审观察者 | `auditor` / `viewer` | 查看告警、安全事件、审计记录与运行时间线 | 全程只读，无任何执行入口 |

角色与"高危操作人工审批流程"（题面功能要求 (2)）的对应：任意 R3/R4 动作必须由发起人之外的审批角色批准后方可下发执行。

> 审批决策接口使用独立权限码 `agent:approve`（迁移 `V8__agent_approval_permission.sql` 引入，授予 platform_admin / org_admin / security_operator），主体集合与 V6 迁移种子的 agent-approval ABAC 策略一致。`incident:respond` 仅用于安全事件处置，不授予 Agent 运行审批能力。功能权限通过后，具体审批单仍由资源级 ABAC 判定风险上限并执行发起人不可自批约束。

## 3. 功能需求

功能需求按官方题面四条功能要求组织。优先级定义：P0=演示主链路必需；P1=完整性必需；P2=增强项。

### 3.1 FR-1x：OS 环境深度感知与 MCP 运维插件化

> 题面原文要点：自动调用 lsof、netstat、journalctl 等获取进程、网络、日志实时上下文；将运维能力插件化封装为标准 Tools。

| 编号 | 需求名称 | 需求描述 | 优先级 | 验收标准 | 系统实现映射 |
|---|---|---|---|---|---|
| FR-101 | 多维系统状态采集 | 实时采集进程、网络连接、监听端口、磁盘、I/O、挂载、内核参数、软件包、用户账户、登录记录、配置权限、防火墙状态 | P0 | 对应只读工具调用均返回结构化结果；覆盖 /proc、ss/lsof、df、rpm、firewalld 等数据源 | 节点侧 32 个只读 MCP 工具（见设计文档 3.2 节分域表） |
| FR-102 | 日志实时上下文获取 | 按服务单元查询 journald 日志，支持行数与优先级过滤，作为推理证据输入 | P0 | `kylin.log.journal_query` 可按 unit/lines/priority 查询白名单服务日志；服务名不在 allowlist 时拒绝 | journalctl 封装工具 + 服务名 allowlist（`service.go` `requireAllowedService`） |
| FR-103 | 一阶段诊断快照 | 单次调用聚合主机资源、进程、网络的只读诊断概要，供推理层快速建立态势 | P1 | `kylin.diagnosis.triage` 返回聚合快照并写入运行事件链 | diagnosis 域工具（R0，模型可在任意轮次自主调用） |
| FR-104 | 指标与安全姿态感知 | 接入 node_exporter 指标快照；探测 KYSEC / SELinux / auditd / security-switch 安全姿态 | P0 | metrics 与 security 域工具可用；安全姿态随心跳上报并触发风险联动（见 FR-208） | node_exporter 采集 + Kylin Native Guard 四件套（`native_guard.go`） |
| FR-105 | MCP 标准协议接入 | 工具层通过 MCP 的工具能力面接入，节点侧提供 `initialize` / `tools/list` / `tools/call` 三个 JSON-RPC 2.0 方法 | P0 | protocolVersion `2024-11-05`；`tools/list` 暴露全部工具定义（含 inputSchema）；`tools/call` 返回 `structuredContent` / `content` / `isError`；未知方法返回 JSON-RPC `-32601` | 节点内嵌 MCP Server（`server.go`），进程内调用 |
| FR-106 | 工具清单声明式注册与签名分发 | 工具以 manifest 声明（id/风险下限/审批要求/只读属性/资源锁模板/输入输出 Schema/幂等语义/实现摘要），以工具包版本形式入库并投影到平台与节点两侧 | P1 | 权威清单 `manifest.json` 可被解析；平台侧与节点侧各持一份投影目录；工具包版本与 SM3 摘要入库可核对 | `tool-packages/core-node-tools/manifest.json` + `tool_package` / `tool_package_version` 表 + `ToolCatalogSigner.java`；工具扩展随版本发布 |
| FR-107 | 工具生态丰富度 | 工具集覆盖磁盘、进程、网络、日志、服务、防火墙、软件包、用户、配置、文件、清理、安全姿态、沙箱 workspace 等真实运维场景，单一职责 | P0 | 权威 manifest 工具总数 = 46（32 只读 / 14 写，其中 10 个 `alwaysRequireApproval`），每个工具单一职责、独立 inputSchema | 46 个 MCP 工具 = 40 个宿主机工具 + 6 个沙箱 workspace 工具 |
| FR-108 | 工具调用全量审计 | 每次工具调用记录工具 id、参数摘要、结果、风险等级、目标节点、耗时与 trace 上下文 | P0 | 任一工具调用可在运行时间线与 `tool_invocation` / `execution_attempt` 表中检索到完整记录，并有对应的 `TOOL_INVOCATION_*` 哈希链事件 | `tool_invocation` + `execution_attempt` + `agent_run_event`（SM3 哈希链） |

对应评分点：MCP 插件丰富度（功能完整性 60% 内第一大项）。

### 3.2 FR-2x：安全意图校验与最小权限执行

> 题面原文要点：建立风险识别规则库，对 LLM 生成指令二次过滤，识别高危参数；以受限账户运行 Agent，非必要不使用 root。

| 编号 | 需求名称 | 需求描述 | 优先级 | 验收标准 | 系统实现映射 |
|---|---|---|---|---|---|
| FR-201 | 风险分级管控 | 所有操作归入官方四级（只读/可逆/不可逆/关键），内部细化为 R0–R5；不可逆操作必须审批，关键操作直接拦截 | P0 | R0/R1 自动执行；R3/R4 无审批不执行；R5 在控制面 `R5_FORBIDDEN` 与节点侧护栏两处 100% 拦截并留痕 | `PolicyEngine.java` R0–R5 + manifest `riskFloor` + `DispatchGate.java` |
| FR-202 | 独立于 LLM 的同步校验 | 安全护栏为确定性规则引擎，不依赖 LLM 推理结果，在执行链路上同步强制生效 | P0 | 关闭/更换 LLM 不影响护栏判定；护栏判定无概率性 | `PolicyEngine.java` / `IntentAlignmentGuard.java` / `DispatchGate.java` / 节点 `runner.go` 均为纯规则实现 |
| FR-203 | LLM 指令二次过滤 | LLM 的 tool_calls 不直接执行；先经工具存在性校验、`additionalProperties:false` 的 Schema 参数校验，再进入 12 步下发门禁，最后由节点侧本地护栏独立复核 | P0 | 未注册工具、越权工具、参数越界的模型输出在门禁处被拒并落 `POLICY_DENIED` / `GRANT_EXCLUDES_TOOL` 等具名事件 | `AgentRoundExecutor.java` → `DispatchGate.java` → `NodeMcpGateway.java` → 节点 `runner.go` |
| FR-204 | 高危参数识别 | 识别敏感路径（/etc、/boot、/var/log/audit、数据库目录等）、非白名单服务、危险参数组合 | P0 | 越界路径/服务的调用在控制面（`POLICY_MANIFEST_BLOCKED_PATH` / `POLICY_MANIFEST_ALLOWED_ROOTS`）与节点侧（`requireAllowedAbsolutePath` / `requireAllowedService`）双端被拒 | manifest allowedRoots/blockedPaths + 节点 `service.go` 参数正则与前缀校验 |
| FR-205 | 动态意图对齐校验 | 校验工具调用与用户原始意图的一致性：咨询型意图不得演变为写操作（如"查看磁盘占用"不得变成"删除日志"） | P0 | 偏离意图的写操作命中 `POLICY_INTENT_MISMATCH` 被拦截；可在「安全试判」页对任意意图 + 工具组合复现判定 | `IntentAlignmentGuard.java` + `DiagnosticsController.java` `/policy` 试判 |
| FR-206 | 可配置策略规则库 | 风险规则支持平台侧 DSL 配置与版本化管理，内置硬底线规则先于 DSL 求值且不可被覆盖 | P1 | 策略变更有版本记录（`safeops_policy_version`）；内置注入 / R5 / manifest 路径规则始终生效 | `PolicyEngine.java` 内置硬规则 + 版本化 Policy DSL |
| FR-207 | 高危操作人工审批 | R3/R4 动作进入审批中心；审批通过后由控制面用 SM2 私钥签发短时令牌，节点侧用公钥独立验真；发起人不可自批 | P0 | 无令牌 / 令牌字段与实际调用不符 / 自批 均被拒绝且留痕（`APPROVAL_BINDING_MISMATCH` / `APPROVAL_ALREADY_CONSUMED`） | `ApprovalService.java` + `Sm2ApprovalTokenService.java` + 节点 `token.go` |
| FR-208 | 本地最终拒绝权与姿态联动 | 节点侧护栏独立复核工具存在性、风险下限、执行模式、审批令牌、资源锁形态与 Native Guard 姿态；姿态危急时拒绝 R3/R4（fail-closed） | P0 | 即使控制面被绕过，节点 `checkLocalGuardrail` 的 13 项校验仍拒绝越权调用；KYSEC / auditd / security-switch 任一 critical 时 R3/R4 被拒 | 节点 `runner.go` `checkLocalGuardrail` + `native_guard_posture.go` |
| FR-209 | 最小权限执行 | Agent 守护进程以专用受限账户运行且进程内**拒绝**执行任何需 root 的命令；写操作一律经 root 特权助手 privhelper（unix socket + SO_PEERCRED + 固定操作映射表 + 独立验签 + root 属主 allow.conf）下沉执行；宿主机命令以 argv 数组直接 exec，无 shell 解释；脚本能力仅存在于隔离沙箱 | P0 | 守护进程以非 root 身份运行；`needsRoot` 的命令在 Agent 进程内被硬拒；宿主机侧不存在通用 shell 工具；`privilege_routing_test.go` 三条不变量测试守恒 | 节点 `service.go`（argv 白名单 + root 硬拒）+ `privops/server.go` + `cmd/privhelper`；部署不使用 sudoers 或 `sudo -n` |
| FR-210 | 执行前备份与校验式回滚 | 清理类不可逆写操作执行前逐文件记录元数据（mode / mtime / uid / gid / SM3）并归档副本，支持按 rollback_id 恢复且恢复后逐文件重算 SM3 比对 | P0 | `kylin.cleanup.execute` 返回 rollback_id 与 backup_path；`kylin.cleanup.rollback` 完整恢复，任一文件哈希不符即返回 `RESTORE_VERIFY_FAILED` 结构化失败 | `cleanupcore/cleanup.go`（备份 `:119-147`、SM3 校验 `:194-202`），元数据落 `/var/lib/kylin-privhelper/rollback/<id>/rollback.json` |

对应评分点：安全校验能力（安全子权重：静态 30% / 动态意图 35% / 受限执行 35%），官方明示为拉开差距的关键项。

### 3.3 FR-3x：抗注入能力与推理链路溯源

> 题面原文要点：识别提示词注入；完整记录"接收指令→感知环境→推理决策→安全校验→执行结果"的闭环日志。

| 编号 | 需求名称 | 需求描述 | 优先级 | 验收标准 | 系统实现映射 |
|---|---|---|---|---|---|

| 清理文件级保护 | 目录放行不等于文件放行：`execute` 只动分类为「临时缓存 / 过期日志 / 长期未修改的非关键文件」的文件；数据库文件、业务配置、凭据、运行时状态、审计与登录证据判为关键保护并拒绝清理，正在写入的活动日志保留。判据（文件名模式 + 扩展名 + mtime）在 root 特权助手侧重跑，不采信守护进程的结论 |

### 5.2 设计约束

- 安全护栏必须是**独立于 LLM 的同步校验机制**：`PolicyEngine` / `IntentAlignmentGuard` / `DispatchGate` / 节点本地护栏 / privhelper 复判均为确定性规则实现，LLM 不参与放行判定；
- 节点侧不保存自然语言会话、不直接调用 LLM、不做规划，只消费经门禁与签名令牌校验的调用（"不可审计则不执行"）；
- **模型不生成命令字符串**：模型只能在已注册工具集内选择工具并给出受 Schema 约束的参数，宿主机命令 argv 由节点侧代码组装，写操作的 argv 更是由 root 助手在自己的进程内组装；
- 国密应用范围：SM3 用于事件哈希链、参数摘要与文件完整性校验；SM2-with-SM3 用于审批令牌签名；PBKDF2-HMAC-SM3 用于口令派生；mTLS 证书采用标准 X.509/TLS 栈；
- RAG 采用向量 / 关键词 / 图谱三路混合检索与 RRF 融合；PostgreSQL 使用 pgvector，H2 演示路径使用内存检索。
