# 软件部署文档

本文档面向系统管理员、实施人员与验收人员，说明麒麟安全智能运维 Agent 的环境准备、安装配置、启动验证和常见故障处理。除特别说明外，命令均在源码仓库根目录执行。

## 1. 交付物与适用环境

### 1.1 交付物目录

源码仓库与 `06-软件安装包及部署文件.zip` 的主要路径对应关系如下。

| 源码仓库路径 | 安装包路径 | 用途 |
|---|---|---|
| `services/backend/target/backend-*.jar` | `backend/backend.jar` | 控制面后端 |
| `apps/admin-web/dist/` | `frontend/admin-web/` | 管理端静态文件 |
| `apps/dashboard-screen/dist/` | `frontend/dashboard-screen/` | 数据大屏静态文件 |
| `agents/node-executor/` 构建产物 | `node-executor/kylin-node-executor-linux-{amd64,arm64,loong64}` | 节点执行器 |
| `agents/node-executor/cmd/privhelper` 构建产物 | `node-executor/kylin-privhelper-linux-{amd64,arm64,loong64}` | 节点特权助手 |
| `agents/workspace-runner/` 构建产物 | `workspace-runner/kylin-workspace-runner-linux-{amd64,arm64,loong64}` | 可选工作区沙箱运行器 |
| `agents/node-executor/deploy/` | `deploy/node-executor/` | 节点 unit、配置样例和验证脚本 |
| `agents/workspace-runner/deploy/`、`Containerfile`、`scripts/` | `deploy/workspace-runner/` | 工作区安装脚本、unit、配置样例与沙箱镜像构建输入 |
| `deploy/docker/stack.yml` | `deploy/docker/stack.yml` | 控制面 Docker Compose 栈 |
| `deploy/observability/` | `deploy/observability/` | Prometheus、Grafana、Tempo 与 OTel 配置 |
| `pom.xml`、`package-lock.json`、`go.mod` | `dependencies/` | Maven、npm 与 Go 依赖清单 |

安装包中的后端、前端和三个节点侧程序均为已构建产物，采用安装包部署时可跳过 Maven、npm 和 Go 构建步骤。

### 1.2 平台适配说明

- 真机实测环境：银河麒麟高级服务器操作系统 V11，aarch64。
- 安装包提供 Linux `amd64`、`arm64`、`loong64` 三种架构的交叉编译二进制。部署时应按 `uname -m` 选择对应文件。
- 三架构二进制交付不等同于三种架构均完成相同范围的整机验证；正式上线前应在目标硬件、内核和安全策略组合上完成验收。
- 控制面可部署在满足 JDK 17 与容器运行要求的 Linux 服务器上。

常见架构映射：

| `uname -m` 输出 | 安装包架构名 |
|---|---|
| `x86_64` | `amd64` |
| `aarch64` | `arm64` |
| `loongarch64` | `loong64` |

### 1.3 第三方依赖获取

交付包不包含 `node_modules`、Maven 本地仓库、系统软件缓存等第三方依赖目录。源码构建和可选组件部署通过受信任的软件源按仓库清单获取依赖：

- 操作系统组件通过 `apt`、`dnf` 或发行版对应的软件源安装；
- Java 依赖由 Maven 按 `services/backend/pom.xml` 下载；
- 前端依赖由 npm 按各应用的 `package-lock.json` 下载；
- Go 模块按各模块的 `go.mod` 下载；节点执行器和工作区运行器使用标准库，可直接采用安装包中的静态二进制；
- 依赖名称、版本与许可证见仓库根目录 `THIRD-PARTY.md`。

离线环境应先在联网构建区完成依赖缓存和制品构建，再按组织的软件供应链流程传入部署区；不得将来源不明的依赖目录直接并入安装包。

## 2. 部署架构与端口

```text
管理端 Web / 数据大屏（nginx 静态站点）
              │ HTTPS / REST / SSE
              ▼
控制面后端（Spring Boot）
  ├─ 8080  REST API / Actuator
  ├─ 9090  gRPC ControlStream（mTLS）
  └─ 9091  gRPC EnrollNode（bootstrap token + CSR）
              │
              │ gRPC mTLS，节点主动连接
              ▼
银河麒麟节点
  ├─ kylin-node-executor.service（User=kylin-agent）
  ├─ kylin-privhelper.service（User=root，仅 AF_UNIX）
  └─ kylin-workspace-runner.service（可选，rootless Podman）

可观测组件（可选）：
OTel Collector → Tempo → Grafana
Prometheus ← backend / node-executor / node_exporter
```

后端任务调度和审批链路使用数据库持久化，不要求部署 Redis 事件总线。Elasticsearch、Milvus、Redis 等仅作为可选 RAG 外部索引组件，按实际检索方案启用。

### 2.1 端口表

| 端口 | 组件 | 用途 | 建议 |
|---|---|---|---|
| 8080 | backend | REST API、SSE、Actuator | 仅内网，经反向代理对外 |
| 9090 | backend gRPC | 节点 ControlStream，mTLS | 仅向节点网段开放 |
| 9091 | backend gRPC | 节点注册 | 仅向节点网段开放 |
| 19100 | node-executor | Prometheus 指标 | 默认绑定 `127.0.0.1` |
| 3001 | Grafana | 指标与 Trace 展示 | 内网 |
| 3200 | Tempo | Trace 查询 | 内网 |
| 9092 | Prometheus | 指标查询 | 内网 |
| 4317 / 4318 | OTel Collector | OTLP gRPC / HTTP | 内网 |
| 9100 | node_exporter | 主机指标，可选 | 内网 |
| 443 / 18080 / 18081 | 反向代理 / 前端 | 用户入口 | 按访问范围开放 |

## 3. 环境准备

### 3.1 源码构建机

| 工具 | 版本 | 用途 |
|---|---|---|
| JDK | 17 或更高 | 后端构建与运行 |
| Maven | 3.9 或更高 | 后端构建 |
| Node.js | 20 或更高，含 npm | 前端构建 |
| Go | 1.26.3 或更高 | 节点程序构建 |
| OpenSSL | 支持 SM2 曲线 | 审批密钥生成 |

### 3.2 运行环境

- 控制面裸机部署：Linux、JDK 17、systemd、nginx。
- 控制面容器部署：Docker Engine 与 Docker Compose v2。
- 节点部署：systemd，以及 `systemctl`、`journalctl`、`firewall-cmd`、`ss`、`lsof`、`df`、`ps`、`top`、`free`、`uptime`、`who`、`ip`、`uname`、`curl`。
- 工作区沙箱：Podman、`newuidmap`、`newgidmap`、systemd-logind 和可用的 subordinate UID/GID 区间。

节点执行器必须使用专用非特权账号 `kylin-agent`。需要特权的受控写操作由 `kylin-privhelper` 执行，不为 `kylin-agent` 配置免密 sudo。

## 4. 源码构建

### 4.1 后端

```bash
cd services/backend
mvn -B -DskipTests package
# 产物：target/backend-0.1.0-SNAPSHOT.jar
```

### 4.2 前端

构建前分别创建 `.env.production`：

```bash
# apps/admin-web/.env.production
VITE_API_BASE_URL=https://<控制面域名>/api/v1

# apps/dashboard-screen/.env.production
VITE_API_BASE_URL=https://<控制面域名>/api/v1
VITE_SCREEN_ORGANIZATION_ID=org-alpha
VITE_SCREEN_TOKEN=<与后端 SCREEN_SHARED_TOKEN 一致的只读 token>
```

执行构建：

```bash
(cd apps/admin-web && npm ci && npm run build)
(cd apps/dashboard-screen && npm ci && npm run build)
```

`VITE_*` 参数会写入前端制品。更换 API 地址、组织标识或大屏 token 后，需要重新构建对应前端。

### 4.3 节点程序交叉编译

```bash
cd agents/node-executor
mkdir -p dist

CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOAMD64=v1 \
  go build -trimpath -ldflags="-s -w" \
  -o dist/kylin-node-executor-linux-amd64 ./cmd/node-executor

CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOAMD64=v1 \
  go build -trimpath -ldflags="-s -w" \
  -o dist/kylin-privhelper-linux-amd64 ./cmd/privhelper

# arm64：GOARCH=arm64
# loong64：GOARCH=loong64
```

Windows 构建机可在 `agents/node-executor` 执行 `build.ps1` 生成三架构 `kylin-node-executor`。`kylin-privhelper` 和 `workspace-runner` 可使用上述 `go build` 方式分别构建。

节点工具目录已编译进 `kylin-node-executor`，节点运行时无需额外放置工具 manifest 或插件目录。

## 5. 控制面部署

### 5.1 数据库模式与迁移

系统支持两种数据库路径：

| 模式 | 配置 | 检索路径 | 适用场景 |
|---|---|---|---|
| H2 | 默认 `jdbc:h2:file:./data/dev-db;MODE=PostgreSQL...` | 向量在 JVM 内存中计算余弦相似度 | 单机演示、快速验证 |
| PostgreSQL + pgvector | 配置 `DEV_DB_*` | 分片向量写入 pgvector，使用 HNSW 余弦索引检索 | 正式部署 |

默认 Flyway 迁移目录为 `services/backend/src/main/resources/db/migration/`，包含 `V1` 至 `V12` 共 12 个迁移文件。

PostgreSQL 模式下，`FlywayConfig` 会自动追加 `classpath:db/postgresql`，并执行仓库中的 3 个 vendor 脚本：

1. `V15_1__enable_pgvector_embedding_column.sql`
2. `V15_2__rag_chunk_pgvector_search.sql`
3. `V57_1__resource_lock_expiry_partial_index.sql`

其中 `V15_2` 在 `app_rag_chunk.embedding` 上建立 pgvector HNSW 余弦索引。使用 PostgreSQL 时应采用已安装 `vector` 扩展的实例；仓库 Compose 栈使用 `pgvector/pgvector:pg16`。

PostgreSQL 连接示例：

```bash
DEV_DB_URL=jdbc:postgresql://127.0.0.1:5432/kylinops
DEV_DB_USERNAME=kylinops
DEV_DB_PASSWORD=<数据库密码>
DEV_DB_DRIVER=org.postgresql.Driver
```

### 5.2 关键环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `HOST_AGENT_SHARED_TOKEN` | 开发配置提供演示值 | 节点注册共享 token，正式部署必须替换 |
| `HOST_AGENT_BOOTSTRAP_TOKEN` | 复用 shared token | EnrollNode bootstrap token |
| `HOST_AGENT_GRPC_CONTROL_PORT` | `9090` | ControlStream 端口 |
| `HOST_AGENT_GRPC_ENROLL_PORT` | `9091` | 注册端口 |
| `HOST_AGENT_GRPC_CERT_DIR` | `./data/host-agent-certs` | 平台 CA 与服务端证书目录 |
| `HOST_AGENT_GRPC_SERVER_DNS_NAMES` | `localhost` | 服务端证书 DNS SAN |
| `HOST_AGENT_GRPC_SERVER_IP_ADDRESSES` | `127.0.0.1` | 服务端证书 IP SAN |
| `APPROVAL_SIGNING_KEY_ID` | `approval-1` | 审批签名密钥标识 |
| `APPROVAL_SIGNING_PRIVATE_KEY_REF` | 空 | 控制面 SM2 私钥绝对路径 |
| `APPROVAL_SIGNING_PUBLIC_KEY_REF` | 空 | 控制面 SM2 公钥绝对路径 |
| `SCREEN_SHARED_TOKEN` | 开发配置提供演示值 | 数据大屏只读 token |
| `STRICT_MODE_ENABLED` | `false` | embedding 严格检查开关 |
| `AUDIT_ELASTICSEARCH_ENABLED` | `false` | 可选审计搜索副本 |
| `RAG_MILVUS_ENABLED` | `false` | 可选 Milvus 索引 |
| `RAG_ELASTICSEARCH_ENABLED` | `false` | 可选 Elasticsearch 关键词索引 |
| `RAG_REDIS_ENABLED` | `false` | 可选 Redis RAG 索引 |

凭证统一写入权限为 `0600` 的本地 env 文件，不写入源码、部署文档或 systemd unit。

`STRICT_MODE_ENABLED=true` 时，后端会对 embedding 配置执行严格检查：向量检索要求管理端配置 `OPENAI_COMPATIBLE` embedding 提供商。该开关不作为服务端 LLM 任务创建的通用硬门控。LLM 可用性应通过管理端模型配置、系统状态接口和部署验收共同确认。

### 5.3 SM2 审批密钥

审批令牌采用 SM2-with-SM3 非对称签名：

- 控制面后端持有私钥并签发令牌；
- 节点 `kylin-privhelper` 仅持有公钥并验签；
- 两端的 key ID 必须一致；
- `kylin-node-executor` 不持有签名密钥。

使用仓库脚本生成密钥：

```bash
sudo bash deploy/scripts/generate-approval-keys.sh /etc/kylinops/keys
sudo chown -R kylinops:kylinops /etc/kylinops/keys
sudo chmod 700 /etc/kylinops/keys
sudo chmod 600 /etc/kylinops/keys/approval-private.pem
```

后端 env：

```bash
APPROVAL_SIGNING_KEY_ID=approval-1
APPROVAL_SIGNING_PRIVATE_KEY_REF=/etc/kylinops/keys/approval-private.pem
APPROVAL_SIGNING_PUBLIC_KEY_REF=/etc/kylinops/keys/approval.pub
```

将同一密钥对的公钥分发到每个节点：

```bash
sudo install -D -m 0644 -o root -g root \
  approval.pub /etc/kylin-privhelper/approval.pub
```

`platform_admin`、`org_admin`、`security_operator` 角色具备 `agent:approve` 权限；具体审批还会经过组织范围、风险上限和“发起人不可自批”等资源级校验。

### 5.4 Docker Compose 部署控制面

源码仓库提供 `deploy/docker/stack.yml`，包含 PostgreSQL/pgvector、后端、管理端和数据大屏：

```bash
cd deploy/docker
cp stack.env.example .env
mkdir -p secrets
cd ../..
bash deploy/scripts/generate-approval-keys.sh deploy/docker/secrets

# 编辑 deploy/docker/.env，替换数据库密码、节点 token、大屏 token 和 Grafana 口令
docker compose -f deploy/docker/stack.yml up -d --build
```

验证：

```bash
docker compose -f deploy/docker/stack.yml ps
curl -fsS http://127.0.0.1:8080/api/v1/system/health
curl -I http://127.0.0.1:18080/
curl -I http://127.0.0.1:18081/
```

`stack.yml` 以源码目录作为镜像构建上下文，适用于源码仓库部署。采用安装包中的预构建制品时，按 5.5 和第 6 节分别部署后端与前端。

### 5.5 systemd 部署后端

```bash
sudo useradd -r -s /sbin/nologin kylinops
sudo install -d -o kylinops -g kylinops /opt/kylinops/backend
sudo install -m 0644 backend/backend.jar /opt/kylinops/backend/backend.jar
sudo install -m 0600 -o kylinops -g kylinops /dev/null /etc/kylinops-backend.env
```

编辑 `/etc/kylinops-backend.env`，配置数据库、节点注册 token、证书 SAN 和审批密钥。创建 `/etc/systemd/system/kylinops-backend.service`：

```ini
[Unit]
Description=KylinOps Control Plane Backend
After=network.target

[Service]
User=kylinops
Group=kylinops
WorkingDirectory=/opt/kylinops/backend
EnvironmentFile=/etc/kylinops-backend.env
ExecStart=/usr/bin/java -jar /opt/kylinops/backend/backend.jar
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now kylinops-backend
curl -fsS http://127.0.0.1:8080/api/v1/system/health
```

仓库还提供 `deploy/scripts/deploy-prod.sh`，可执行后端和前端的 SSH 推送、systemd 重启与健康检查。运行前复制并填写 `deploy/config/prod.env.example`：

```bash
cp deploy/config/prod.env.example deploy/config/prod.env
chmod 600 deploy/config/prod.env
./deploy/scripts/deploy-prod.sh backend,admin,screen
```

### 5.6 模型与 embedding 配置

部署后使用具备 `platform:configure` 权限的账号进入管理端“模型配置”页面（路由 `/platform-llm`）：

1. 新增 LLM 提供商配置并完成连通性测试；
2. 启用供 Agent Runtime 使用的模型配置；
3. 在 RAG 设置中配置 embedding 提供商；
4. 需要语义向量检索时选择 `OPENAI_COMPATIBLE` 并填写可用端点、模型和维度；
5. 修改 embedding 模型或维度后，按管理端操作执行知识库向量重建。

`LOCAL` embedding 用于离线功能验证，不提供语义向量能力。H2 模式采用 JVM 内存检索；PostgreSQL 模式在 pgvector 中完成分片向量排序。

## 6. 前端部署

将预构建静态文件发布到 nginx。管理端示例：

```nginx
server {
  listen 18080;
  server_name _;
  root /opt/kylinops/admin-web;

  location / {
    try_files $uri $uri/ /index.html;
  }

  location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

```bash
sudo install -d /opt/kylinops/admin-web /opt/kylinops/dashboard-screen
sudo cp -R frontend/admin-web/. /opt/kylinops/admin-web/
sudo cp -R frontend/dashboard-screen/. /opt/kylinops/dashboard-screen/
sudo nginx -t
sudo systemctl reload nginx
```

数据大屏可使用独立 `server` 块和端口 18081，根目录指向 `/opt/kylinops/dashboard-screen`。

## 7. 银河麒麟节点部署

### 7.1 安装节点执行器与特权助手

```bash
ARCH=arm64  # 根据 1.2 节选择 amd64、arm64 或 loong64

sudo useradd -r -s /sbin/nologin kylin-agent
sudo install -d -o kylin-agent -g kylin-agent /opt/kylin-security-ops-agent
sudo install -d -o kylin-agent -g kylin-agent /var/lib/kylin-node-executor/certs

sudo install -m 0755 node-executor/kylin-node-executor-linux-$ARCH \
  /opt/kylin-security-ops-agent/kylin-node-executor
sudo install -m 0755 node-executor/kylin-privhelper-linux-$ARCH \
  /opt/kylin-security-ops-agent/kylin-privhelper

sudo chown kylin-agent:kylin-agent \
  /opt/kylin-security-ops-agent/kylin-node-executor
sudo chown root:root \
  /opt/kylin-security-ops-agent/kylin-privhelper
```

### 7.2 配置特权助手

安装允许清单、清理范围配置、审批公钥和 systemd 物料：

```bash
sudo install -D -m 0644 -o root -g root \
  deploy/node-executor/privhelper-allow.conf.example \
  /etc/kylin-privhelper/allow.conf

sudo install -D -m 0644 -o root -g root \
  deploy/node-executor/cleanup.conf.example \
  /etc/kylin-privhelper/cleanup.conf

sudo install -D -m 0644 -o root -g root \
  approval.pub /etc/kylin-privhelper/approval.pub

sudo install -m 0644 deploy/node-executor/kylin-privhelper.tmpfiles \
  /usr/lib/tmpfiles.d/kylin-privhelper.conf
sudo systemd-tmpfiles --create /usr/lib/tmpfiles.d/kylin-privhelper.conf

sudo cp deploy/node-executor/kylin-privhelper.service /etc/systemd/system/
```

编辑 `/etc/kylin-privhelper/allow.conf`：

```text
allowed_units=nginx,business-service
allowed_scopes=ingress
max_block_minutes=60
max_ops_per_minute=30
```

如需启用文件清理，`cleanup_allowed_dirs`、unit 的 `ReadWritePaths` 和目标目录权限必须保持一致。不要将系统根目录、数据库目录或审计目录加入清理范围。

### 7.3 配置节点执行器

```bash
sudo install -m 0600 -o kylin-agent -g kylin-agent \
  deploy/node-executor/kylin-node-executor.env.example \
  /etc/kylin-node-executor.env
sudo vi /etc/kylin-node-executor.env
```

至少配置：

```bash
KYLIN_ENROLLMENT_TOKEN=<与后端 HOST_AGENT_SHARED_TOKEN 一致>
KYLIN_GRPC_ENROLL_ADDRESS=<控制面IP>:9091
KYLIN_GRPC_CONTROL_ADDRESS=<控制面IP>:9090
KYLIN_NODE_EXECUTOR_CERT_DIR=/var/lib/kylin-node-executor/certs
KYLIN_ENROLL_CA_FILE=/etc/kylin-node-executor/platform-ca.crt
KYLIN_ENROLL_SERVER_NAME=<控制面证书中的 DNS 名称>
KYLIN_CONTROL_SERVER_NAME=<控制面证书中的 DNS 名称>
KYLIN_PRIVHELPER_SOCKET=/run/kylin-privhelper/helper.sock
```

将控制面 `HOST_AGENT_GRPC_CERT_DIR/ca.crt` 安全复制到节点的 `KYLIN_ENROLL_CA_FILE`。也可使用 `KYLIN_ENROLL_CA_SHA256` 进行证书指纹钉扎。`KYLIN_ENROLL_INSECURE_TOFU=true` 仅适用于隔离的开发环境。

Agent 侧的 `KYLIN_ALLOWED_SERVICES`、`KYLIN_ALLOWED_BLOCK_SCOPES` 与助手侧 `allow.conf` 均需授权，写操作才可执行。

### 7.4 启动与验证

```bash
sudo cp deploy/node-executor/kylin-node-executor.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now kylin-privhelper
sudo systemctl enable --now kylin-node-executor

systemctl is-active kylin-privhelper kylin-node-executor
sudo journalctl -u kylin-privhelper -n 30 --no-pager
sudo journalctl -u kylin-node-executor -n 50 --no-pager
curl -fsS http://127.0.0.1:19100/metrics
```

节点首次启动时会生成私钥与 CSR，使用 bootstrap token 调用 9091 注册，并将平台签发的节点证书保存到证书目录；后续控制流通过 9090 mTLS 建立。

仓库验证脚本：

```bash
sudo bash deploy/node-executor/verify-kylin-node.sh
sudo bash deploy/node-executor/verify-kylin-runtime.sh
sudo bash deploy/node-executor/verify-kylin-stability.sh
```

### 7.5 可选工作区沙箱

`kylin.workspace.bash/python/read/write/edit/glob` 六个工具依赖 `workspace-runner`。该组件以独立 systemd 服务运行，通过 Unix socket 调用 rootless Podman 沙箱。

安装前提：

- 节点已安装并启动 Podman；
- `newuidmap`、`newgidmap` 和 `/etc/subuid`、`/etc/subgid` 可用；
- systemd-logind 支持为 `kylin-workspace` 启用 linger；
- 沙箱镜像构建上下文包含 `agents/workspace-runner/Containerfile` 与 `scripts/`；
- 运行器 socket 与 Agent 的 `KYLIN_WORKSPACE_RUNNER_SOCKET` 配置一致。

在源码仓库执行；如采用安装包中的预编译二进制，将其绝对路径作为参数传入：

```bash
sudo agents/workspace-runner/deploy/install-workspace-runner.sh \
  /path/to/kylin-workspace-runner-linux-<arch>

systemctl status kylin-workspace-runner
ls -l /run/kylin-workspace/workspace.sock
```

若使用安装包中的预编译二进制，应先准备同版本源码中的容器镜像构建上下文，再执行安装脚本。部署该组件后重启 `kylin-node-executor`，使其重新获取组成员权限并连接 socket。

## 8. 可观测组件

在源码仓库中启动控制面与可观测叠加栈：

```bash
docker compose \
  -f deploy/docker/stack.yml \
  -f deploy/docker/observability.yml \
  up -d --build

./deploy/observability/scripts/verify-observability.sh
```

组件包括 OTel Collector、Tempo、Prometheus 与 Grafana。有效的预置面板覆盖：

- 纳管主机数与 gRPC 连接节点数；
- Node Executor 在线状态与累计完成、失败、拒绝任务；
- Native Guard 风险主机；
- 活跃资源锁；
- Node Executor 按风险等级统计的运行与排队任务。

接入要求：

- 后端使用 OpenTelemetry Java Agent，将 OTLP HTTP 发送至 Collector 4318；
- 节点设置 `KYLIN_OTEL_ENABLED=true`，将 OTLP gRPC 发送至 Collector 4317；
- 跨容器抓取节点 19100 端口时，将指标地址改为 `0.0.0.0:19100`，并用防火墙限制来源；
- node_exporter 由操作系统软件源安装；
- `/actuator/prometheus` 需要认证，Prometheus backend job 应配置有效的 Bearer token。

## 10. 安全配置要求

1. 正式部署前替换所有示例口令、注册 token、大屏 token 与 Grafana 默认口令。
2. 后端 env、节点 env 和部署 env 权限设为 `0600`，并由对应服务账号持有。
3. 控制面 SM2 私钥只保存在控制面；节点只部署公钥。
4. 后端 CA 私钥目录应纳入加密备份和访问审计。
5. 节点执行器以 `kylin-agent` 运行，不配置免密 sudo；特权助手的二进制、配置、公钥和状态目录由 root 管理。
6. 8080、9090、9091、19100、Prometheus、Tempo 与 Grafana 端口按最小网络范围开放。
7. 注册过程使用 CA 文件或证书指纹钉住平台身份；公网或生产网络禁用 TOFU。
8. 清理范围只配置业务明确授权的目录，并同时校验 systemd `ReadWritePaths` 和目录属主。
9. PostgreSQL、前端制品、CA 目录、审批密钥和审计数据应纳入备份与恢复演练。

## 11. 故障处理

| 现象 | 可能原因 | 处理方法 |
|---|---|---|
| 后端启动报 Flyway checksum mismatch | 数据库迁移历史与当前制品不一致 | 先备份数据库，核对 schema 差异，再按变更流程执行 Flyway repair；禁止直接删除迁移历史 |
| PostgreSQL 启动迁移报 vector 扩展错误 | 使用了普通 PostgreSQL 镜像或实例无 pgvector | 安装 pgvector 扩展，或使用 `pgvector/pgvector:pg16` |
| Agent 注册提示 token 错误 | 两端 token 不一致或 env 未加载 | 核对 `KYLIN_ENROLLMENT_TOKEN` 与后端 token，重载 unit 后重启 |
| Agent 拒绝 enroll，提示需要 pinned platform identity | 缺少 CA 文件或指纹 | 配置 `KYLIN_ENROLL_CA_FILE` 或 `KYLIN_ENROLL_CA_SHA256` |
| 证书指纹不匹配 | 服务端证书轮换或连接目标异常 | 先确认轮换记录和目标地址，再重新获取并核对指纹 |
| 节点显示 disconnected | 控制流地址、防火墙、证书或服务状态异常 | 检查 9090 连通性、节点日志、证书有效期与吊销状态 |
| 写操作提示特权助手不可达 | helper 服务停止或 socket 路径不一致 | 检查 `kylin-privhelper` 状态，并核对两端 socket 配置 |
| helper 因配置权限退出 | 配置或公钥属主、写权限不符合要求 | 设置 `root:root`，移除 group/other 写权限后重启 |
| 审批令牌校验失败 | key ID、公钥、TTL 或身份字段不匹配 | 核对两端 key ID 和密钥对，重新发起审批 |
| 工作区工具连接失败 | runner、Podman、组成员或 socket 配置异常 | 检查 runner 日志、Podman rootless 环境和 socket 权限，重启 Agent |
| Prometheus backend job 返回 401 | 抓取请求缺少认证 | 为 backend job 配置有效 Bearer token |
| Grafana 无节点指标 | 19100 仅绑定本机或 node_exporter 不可达 | 调整监听地址并限制来源，检查抓取目标 |
| 大屏 401 | 构建时 token 与后端不一致 | 修正 `VITE_SCREEN_TOKEN` 后重新构建发布 |
| 向量检索在严格模式下被拒绝 | embedding 提供商不是 `OPENAI_COMPATIBLE` | 在管理端配置可用的语义 embedding，并按模型维度重建向量 |
| RAG 外部栈与注册端口冲突 | Milvus 与 gRPC enroll 同用 9091 | 修改其中一方端口映射并同步配置 |
