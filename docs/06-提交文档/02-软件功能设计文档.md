# 软件功能设计文档

## 1. 总体架构

### 1.1 逻辑分层与部署映射

系统采用"平台侧智能体大脑 + 节点侧受控执行 Agent"两级部署，感知、推理决策和安全护栏在两级部署中的分工：

| 逻辑层 | 本系统组件 |
|---|---|
| 多维感知层 Perception | 节点采集工具（46 个 MCP 工具中的 32 个只读工具）+ 心跳/能力上报 + node_exporter 指标 + Kylin Native Guard 安全姿态四件套 |
| 推理决策层 Reasoning | `AgentRunWorker` 租约轮询 + `AgentRoundExecutor` 原生 function-calling ReAct 主循环 + 上下文编译/压缩 + 记忆与 RAG 三路混合检索 + 子 Agent 招募与交接 |
| 安全控制层 Safety Guardrail | `DispatchGate` 十二步下发门禁（授权 grant / PolicyEngine 静态规则与注入黑名单 / IntentAlignmentGuard 意图对齐 / R5 硬禁 / 执行模式 / ABAC 工具维 / 专家注册表能力封套 / ABAC 主机维 / Native Guard 姿态 / 审批）+ 节点本地护栏（最终拒绝权）+ privhelper 独立验签复判——全部为**独立于 LLM 的同步校验机制** |

## 2. 推理决策设计：ReAct 主循环与计划门控

### 2.1 架构设计

系统采用 **单一 ReAct 主循环 + 计划门控**。模型通过原生 function-calling 逐轮选择工具，所有工具调用在执行前进入确定性门禁；执行模式、授权范围、预算和不可变 Plan 文档共同约束运行边界。

| 关注点 | 承载机制 | 实现位置 |
|---|---|---|
| 局部灵活（该看哪、下一步做什么） | 模型原生 function-calling 迭代 | `AgentRoundExecutor.java` |
| 全局可控（能做到多大范围） | 执行模式 PLAN / CAUTIOUS / AUTO | `DispatchGate.java` + proto `ExecutionMode` |
| 全局可控（能用哪些工具、哪些主机） | 运行授权范围 grant（toolIds / nodeIds / readOnly） | `DispatchGate.java` 前两步 |
| 全局可控（能烧多少） | 五类预算：模型调用 / 工具调用 / 墙钟 / 写次数 / 停滞轮数 | `AgentRoundExecutor.java` `BudgetLimits` |
| 全局可控（方案本身要不要先批） | 不可变 Plan 文档 + 版本化 AMEND + 从计划启动新 run | `PlanService.java` / `plan_version` 表 |

上述四类约束在每一轮、每一次工具调用时重新求值，以降低检查时状态与使用时状态不一致的风险。

### 2.2 ReAct 主循环与执行链路

```text
① REST 入口  POST /api/v2/agent-runs
   AgentRunController：校验执行模式正则、objective、grant、budget
   → 落 agent_run(QUEUED)，立即返回 runId（不阻塞在模型调用上）
   │
② AgentRunWorker  @Scheduled(fixedDelay 250ms)
   store.leaseNext() 抢租约（多实例安全）→ 交给 AgentRoundExecutor
   │
③ AgentRoundExecutor —— function-calling ReAct 主循环（默认最多 8 轮）
   轮首：检查五类预算 → 写 agent_run_checkpoint(round_no)
   ContextCompiler 编译上下文（超窗则 ContextSummarizer 确定性压缩最旧轮次）
   → ModelGateway 调模型（MODEL_INVOCATION_STARTED/COMPLETED 入事件链）
   → 模型返回 tool_calls
   │
④ 逐个 tool_call 过 DispatchGate（十二步门禁，见 §4.1）
   ├ REJECTED       → 具名错误码入事件链，观察结果回填给模型，继续下一轮
   ├ NEEDS_APPROVAL → 建审批单，run 转 WAITING，退出循环（等人）
   └ ALLOWED        → 签发 SM2 审批令牌（若需要）→ NodeMcpGateway
   │
⑤ NodeMcpGateway
   工具参数按 inputSchema 校验 → 规范化 JSON → SM3 摘要
   → 计算资源锁 → 组装 SubmitInvocation → 经 gRPC ControlStream 下发
   │
⑥ 节点侧（见 §4.6 / §4.7）
   ControlStream Client → safeops.Scheduler → safeops.Runner
   → 三路分发（进程内 MCP / privhelper / 沙箱）
   │
⑦ InvocationResult 回流 → 写 tool_invocation / execution_attempt
   → 观察结果回填模型上下文 → 回到 ③ 下一轮
   │
⑧ 终止：模型不再要工具（RUN_COMPLETED）/ 预算触顶 / 停滞 / 失败 / 取消
```

**审批不是阻塞等待，是状态机。** 命中 NEEDS_APPROVAL 时 run 落 `WAITING` 并释放租约；人在审批中心决定后，`ApprovalService` 唤醒 run（`RUN_WAKEUP`），执行器"确定性地补齐"那一次被批准的调用——批准的是哪一次调用就只执行哪一次，不重新问模型。

### 2.3 执行模式的语义

| 模式 | 语义 | 门禁行为 | 三处独立强制点 |
|---|---|---|---|
| `PLAN` | 只读勘察，产出方案不落地 | 风险 ≥ R2 一律 `PLAN_MODE_FORBIDS_WRITE` 拒绝 | 控制面 `DispatchGate` / 节点 `runner.go` / privhelper `Handle` 各判一次 |
| `CAUTIOUS`（默认） | 写操作必须人工审批 | 需审批的工具一律进审批单 | 同上 |
| `AUTO` | 低风险写自动放行 | 风险 ≤ `auto-risk-ceiling`（默认 R2）自动批准并记 `APPROVAL_AUTO_GRANTED`；R3+ 仍需人工 | 同上 |

前端在从非 AUTO 切到 AUTO 时强制二次确认（说明"≤R2 写操作将无需人工审批"），避免误开。

### 2.4 LLM 不可用时的确定性只读保障

当已配置模型暂时不可用时，系统可执行确定性只读剧本（`AgentRoundExecutor.java` 的 `runDeterministicFallback` 与同包 `model/DeterministicFallbackPlaybook`），采集基础诊断信息并保持门禁与审计要求不变。

**触发条件**：某一轮中全部已配置模型 profile 都不可用（重试已耗尽）。

**四条链，按命中关键词数选优**（同分取先声明者，因此结果完全确定、可复现）：

| 链 | 关键词（节选） | 步骤（全部只读） |
|---|---|---|
| 磁盘与清理诊断 | 磁盘 / 空间 / 容量 / 占用 / 清理 / 满了 / disk / cleanup | `disk.usage` → `system.mounts` → `disk.large_files` → `cleanup.plan` |
| 安全姿态巡检 | 安全 / 加固 / 合规 / 审计 / 入侵 / 封禁 / kysec / selinux / auditd | `security.kysec_status` → `selinux_status` → `auditd_status` → `security_switch_status` → `firewall.state` |
| 服务与日志诊断 | 服务 / 重启 / 挂了 / 日志 / 报错 / service / journal / nginx | `net.listening_ports`（+ 提供了服务名时追加 `service.status` → `log.journal_query`） |
| 进程与资源诊断 | 进程 / cpu / 内存 / 负载 / 卡 / 慢 / 性能 / process / load | `process.top_cpu` → `process.top_memory` → `io.snapshot` → `metrics.node_exporter_snapshot` |

**三条硬约束**：

1. **只读**——剧本里只允许出现只读工具；执行前还按工具目录的 `readOnly` 位再筛一次（双保险），并且每一步**照常过 DispatchGate**，grant / ABAC / 风险门禁一个都不少，被拒的步骤标记 `SKIPPED` 并记录拒绝码；
2. **确定性**——关键词 → 固定工具链，无任何模型参与；目标服务名缺失时，需要服务名的步骤**整体略过而不是猜一个**；
3. **可识别**——匹配不到适用链时终止本次运行；进入只读保障路径时写入 `MODEL_UNAVAILABLE_FALLBACK` 事件，结果标记 `degraded=true` / `degradedReason=MODEL_UNAVAILABLE`，并注明结果来自固定只读工具链。这些调用不设置 `agentInvocationId`，以保持事件因果关系准确。

管理端在未配置可用模型时禁用任务发送入口并提示完成模型配置。后端在模型调用失败时按既定路由执行同租户模型档案切换，并在全部档案不可用时进入确定性只读诊断流程。严格模式用于校验语义向量服务配置，不作为服务端任务创建的通用门控。

### 2.5 RAG 辅助根因分析

- **检索口径**：三路召回 + RRF 融合。默认配置 `RetrievalConfig.defaults` = 向量 / 关键词 / 图谱三通道全开，通道权重 `1.0 / 1.0 / 0.8`，`rrfK=60`，`candidateN=50`；某文档的融合得分 = Σ(通道权重 / (60 + 该通道内排名))；
- **可选交叉重排**：融合后可接 cross-encoder 重排（RRF 只看位次，重排才看真实语义匹配度）；重排服务不可用时退回融合序；
- **存储适配**：PostgreSQL 部署使用 pgvector 完成向量检索；H2 演示路径使用 JVM 内存检索；关键词路可按配置接入 Elasticsearch，图谱路使用知识图谱关系召回；
- **可溯源**：命中的知识来源随回答返回并在前端展示（标题 / 来源类型 / 得分）。三通道相对二通道的实测差异（召回基本持平、时延增加约 80 ms，价值在关系解释与多跳证据）见《性能核心指标测试报告》。

## 3. MCP 工具体系

### 3.1 MCP JSON-RPC 2.0 Server（`server.go`）

节点内嵌 MCP Server，提供工具能力面所需的三个方法。`runner.go` 在进程内调用 `server.Handle`，MCP 用于承载工具契约与 Schema 校验。

| 方法 | 说明 |
|---|---|
| `initialize` | 协议握手：`protocolVersion` = `2024-11-05`，`serverInfo` = `kylin-node-executor`，`capabilities.tools.listChanged = true` |
| `tools/list` | 返回全部工具定义（含 inputSchema、风险注解） |
| `tools/call` | 校验 name 非空 → catalog 查表 → **inputSchema 校验**（`additionalProperties:false`、required、enum、minLength、integer 上下界）→ 调用 Go handler → 返回 `structuredContent` + `content` + `isError` |
| 其他方法 | 一律返回 JSON-RPC `-32601 method not found`；`jsonrpc` 字段非 `"2.0"` 返回 `-32600` |

工具级失败**不**表达为 JSON-RPC error，而是 `CallResult{isError:true}`，以便把结构化的失败原因原样带回控制面事件链。

### 3.3 Manifest 声明式注册与版本化分发

权威工具清单是 `tool-packages/core-node-tools/manifest.json`（46 条），按工具包版本入库（`tool_package` / `tool_package_version`），并投影为平台侧与节点侧各一份目录文件。每个工具的安全元数据：

| 字段 | 作用 |
|---|---|
| `riskFloor` | R0–R5 风险下限，节点侧对下发风险低于下限的调用直接拒绝（防降险绕过） |
| `alwaysRequireApproval` / `readOnly` | 强制审批标记与读写属性 |
| `executor` | 执行面归属：`NODE`（宿主机）或 `WORKSPACE`（沙箱） |
| `resourceLocks` | 资源锁模板（`path:{targetDir}` / `service:{unit}`，READ_SHARED / WRITE_EXCLUSIVE） |
| `inputSchema` / `outputSchema` | JSON Schema 参数与结果约束（`additionalProperties:false` 防参数走私） |
| `idempotency` | 幂等语义（IDEMPOTENT / AT_MOST_ONCE / NON_RETRYABLE）与 `maxAttempts` |
| `reversibility` | 可逆性声明（REVERSIBLE / COMPENSATING / NO_INVERSE），供策略引擎对不可恢复动作升险 |
| `implementation.digest` | 实现摘要，用于清单与实现的一致性核对 |

工具扩展采用版本化发布。扩展只读工具需补充 manifest 与 handler；扩展写工具还必须在 privhelper 的固定操作映射表中显式登记，确保特权能力变更可审查、可追踪。

### 3.4 沙箱即边界：workspace 工具不构成宿主机通用 shell

`kylin.workspace.bash` / `kylin.workspace.python` 在隔离容器内执行脚本，与"给 Agent 一个宿主机 shell"是两回事——**边界不在语法层，而在执行环境层**：

| 维度 | 宿主机工具（40 个） | workspace 沙箱工具（6 个） |
|---|---|---|
| 执行位置 | 宿主机 OS，固定 argv 白名单命令 | rootless Podman 容器内，与宿主机隔离 |
| 宿主机文件系统 | 受 allowedRoots / blockedPaths 约束 | 完全不可见（不挂载宿主机路径） |
| 网络 | 按工具授权 | 无网络（network=none） |
| 根文件系统 | 不适用 | 只读（read-only rootfs） |
| 权限 | 非 root，需 root 的命令在 Agent 进程内被硬拒，一律下沉 privhelper | rootless + `cap-drop=ALL` + `no-new-privileges` + 自定义 seccomp |
| 风险与审批 | 写工具 R3 强制人工审批 | R1，受同一套 DispatchGate / ABAC / 预算约束 |

沙箱内脚本无法读取宿主机文件、无法访问网络、无法提权，也不能对宿主机产生副作用。因此不构成对目标主机执行任意命令的通道。6 个 workspace 工具依赖独立的 `workspace-runner` 与 Podman 运行环境；未配置该运行条件时，仅宿主机约 40 个工具可用。

## 4. 安全控制设计

### 4.1 DispatchGate：下发前的十二步确定性门禁

下发门禁是系统统一的**执行强制点**：模型产出的每一个工具调用在离开控制面之前必须逐条通过下列判定。判定顺序与 `DispatchGate.java` 的 `evaluate` 方法一致；任一步不满足条件即返回结构化拒绝码并写入事件链。门禁位于下发路径，可覆盖首轮执行、断点续跑和审批恢复等路径，并在每个下发周期重新判定。

| # | 判据 | 拒绝码 | 说明 |
|---|---|---|---|
| 1 | 运行授权范围的工具白名单 | `GRANT_EXCLUDES_TOOL` | run 声明了 grant.tools 时，越表即拒 |
| 2 | 运行授权范围的只读约束 | `GRANT_READ_ONLY` | run 声明只读时，写工具即拒 |
| 3 | `PolicyEngine.evaluate` → `IntentAlignmentGuard.align` | `POLICY_INTENT_MISMATCH` / `POLICY_DENIED` | 内置硬底线规则（注入话术、禁止动作、关闭 Native Guard、manifest blockedPaths / allowedRoots）先于可配置 DSL 求值，DSL 无法放宽硬底线；意图为咨询而工具为写 → 失配拒绝 |
| 4 | R5 无条件禁止 | `R5_FORBIDDEN` | 定级 R5 直接拒绝，不进入任何后续判定 |
| 5 | 只读模式禁写 | `PLAN_MODE_FORBIDS_WRITE` | `executionMode == PLAN` 且风险 ≥ R2 即拒 |
| 6 | 运行授权范围的节点白名单 | `GRANT_EXCLUDES_NODE` | run 声明了 grant.nodes 时，越表即拒 |
| 7 | ABAC 第一维：工具 | `ABAC_DENIED` | `resourceType="agent-tool"`，action=`execute`，context 携带 risk 与 nodeId |
| 8 | 专家注册表能力封套（Agent IAM） | `AGENT_ENVELOPE_DENIED` | 仅当本次调用由**绑定了专家身份**的 Agent 发起（`agent_instance.registry_agent_key` 非空）：按 `app_agent_registry` 的 allowed_tools + max_risk + enabled 做 fail-closed 判定（未注册 / 已停用 / 工具越封套 / 风险超上限 → 拒）。`agentKey` 为空（人直接发起的根 Agent、存量 run）→ **不判定** |
| 9 | ABAC 第二维：主机 | `ABAC_DENIED_HOST` | `resourceType="HOST"`，resourceId = 目标 nodeId，action 按风险映射（≥R2 → `operate`，只读 → `read`）。与第一维**串联**：任一维 DENY 即拒，两维都无匹配 ALLOW 也拒（default-deny） |
| 10 | Native Guard 姿态新鲜度 | `NATIVE_GUARD_<STALE\|UNKNOWN\|…>` | 仅对 R3+：姿态非 FRESH 即拒（不可验证则不放行） |
| 11 | Native Guard 姿态危急 | `NATIVE_GUARD_CRITICAL` | 仅对 R3+：姿态新鲜但为 CRITICAL 即拒 |
| 12 | 审批判定 | → `NEEDS_APPROVAL` 或 `ALLOWED` | `requiresApproval \|\| alwaysRequireApproval` 时：`AUTO` 模式且风险 ≤ `auto-risk-ceiling`（默认 R2）→ 自动批准（`APPROVAL_AUTO_GRANTED`）；否则建审批单。均不成立则 `ALLOWED` |

主机维 ABAC 将 `nodeId` 作为被判定资源，以主体、资源类型、资源标识、动作和条件共同完成授权。Agent IAM 能力封套仅适用于绑定了注册专家身份的子 Agent；根 Agent 与未绑定注册专家身份的运行实例不附加该封套，仍受用户授权范围、工具与主机 ABAC、执行模式和风险策略约束。

### 4.1.1 三处独立强制点

门禁通过之后，同一批安全判据还会被**另外两个进程**独立重做一遍。这不是冗余，而是信任边界的划分——每一层都假设上一层已被攻陷：

```text
【控制面 · DispatchGate】十二步门禁 → 签发 SM2 审批令牌
   │  gRPC + mTLS，SubmitInvocation 携带风险/令牌/锁/deadline/traceparent
   ▼
【节点守护进程 · safeops.Runner】本地护栏 13 项复核（最终拒绝权）
   身份与 trace 完整性 → 工具在册 → 风险可识别(未知即拒)
   → R5 拒 → PLAN 模式禁写 → 风险不得低于 manifest riskFloor
   → R3/R4 必须有令牌且形态合法 → R3/R4 必须有资源锁且为写排他
   → R3/R4 触发 Native Guard 姿态复判（KYSEC / auditd / security-switch 任一 critical 即拒）
   │  任一不过 ──► 本地拒绝 + 事件回传
   ▼  写操作 → unix socket
【root 特权助手 · privhelper.Handle】独立验签 + 独立复判
   SM2 公钥验签(签名覆盖 17 字段) → 13 身份字段逐字段复判 → 一次性消费
   → 操作必须在固定映射表内 → PLAN 模式独立复判 → R5 独立复判 → 限流
   → **自行组装 argv**（命令行从不由守护进程传入）→ 执行
```

守护进程**不**验证审批令牌的真伪，只检查形态；真正的验签在 root 助手里。这是有意的降级：守护进程是被攻陷概率最高的一环，把验签放在它那里等于把公钥信任也交给了它。相应地，`privilege_routing_test.go` 用三条不变量测试锁死了这个前提——每个需 root 的工具都必须可路由到助手、且绝不在守护进程内本地执行、每个强制审批的工具都必须走助手。

### 4.2 风险分类与 R0–R5 等级

| 风险类别 | 内部等级 | 含义 | 默认策略 |
|---|---|---|---|
| 只读 | R0 / R1 | 只读查询 / 低风险可逆 | 自动执行，可并行 |
| 可逆 | R2 | 改变临时状态、可恢复 | 限制并行，需确认 |
| 不可逆 | R3 / R4 | 改文件/服务/网络 / 关键配置与敏感路径 | **人工审批 + 备份回滚**，写操作串行；R4 强审批或默认拒绝 |
| 关键 | R5 | 格式化、批量删除、注入指令等明确禁止动作 | **直接拦截**并审计留痕 |

### 4.3 Prompt 注入防护

- 注入黑名单覆盖"忽略之前所有规则 / 不要记录日志 / 绕过审批 / 你现在是 root / 禁用安全策略 / 删除所有"等中英双语模式，命中即 R5（`POLICY_R5_FORBIDDEN_OR_INJECTION`）；另有一组专门针对"关闭 KYSEC / auditd / 安全开关"的禁止动作规则（`POLICY_R5_NATIVE_GUARD_DISABLE`）；
- 防护位于规则引擎而非 LLM 提示词中，**模型更换不影响防护效果**；
- 静态拦截事件本身落哈希链（满足"拦截留痕"要求）；
- **只读工具对文本硬规则的有限豁免**：若文本规则对所有工具无条件生效，受污染的运行目标会使诊断类只读调用一并被拒绝，影响安全事件分析。因此文本规则对只读工具设置有限豁免，对写工具仍保持强制约束；模型输出异常时仍无法获得写操作权限；
- 纵深防御：即使注入诱导模型产出越权 tool_calls，仍需通过 Schema 校验、意图对齐、ABAC 双维、审批、节点本地护栏与 root 助手复判六道闸门；
- **可现场验证**：「安全试判」页的 Policy 试判面板直接调用与生产同序的 `PolicyEngine.evaluate → IntentAlignmentGuard.align`，输入任意意图 + 工具即可看到风险定级、是否拦截、命中的硬规则 ID 与策略版本。

### 4.4 审批令牌设计（SM2-with-SM3 非对称签名）

**算法**：控制面用 SM2 私钥签发，节点侧 root 助手用公钥验真。域分隔用户标识为 `KYLIN-APPROVAL-V1`，密钥用途常量 `approval-signing-key` 参与签名，防止密钥跨用途混用。

**签名覆盖范围**：proto `ApprovalClaim` 的**全部 17 个字段**（含 version / key_purpose / issued_at / expires_at）。

**节点侧逐字段复判范围**：其中 **13 个身份字段**——

```text
tenant_id · run_id · agent_instance_id · agent_invocation_id · tool_invocation_id
execution_attempt_id · node_id · tool_id · tool_version · arguments_sm3
risk_ceiling · execution_mode · lock_version
```

比对规则：`risk_ceiling` 允许"实际风险 ≤ 批准上限"，**其余 12 个必须精确相等**。其中 `arguments_sm3` 是参数 JSON 的 SM3 摘要——改一个字节参数，令牌立即失配。

**fail-closed 的取值映射**：节点侧把请求投影成 claim 时，无法识别的风险码映射为 `R5`、无法识别的执行模式映射为 `UNSPECIFIED`；而合法 claim 的 `risk_ceiling` 被约束在 R0–R4、`execution_mode` 被约束为 CAUTIOUS 或 AUTO——因此任何"看不懂的请求"都不可能被任何合法令牌覆盖。

**时效与消费**：有效期上限 5 分钟（超出即拒签），验真时校验 `issuedAt`（含 30 秒时钟偏移宽限）与 `expiresAt`；令牌 SM3 指纹写入 privhelper 的**持久化消费台账**（fsync 落盘后才执行），重放直接拒绝并审计，且**跨助手重启有效**。

**发起人不可自批**：审批人与运行发起人强制分离。

> **一次性消费是持久化的**：令牌 SM3 指纹写入 privhelper 的 root-only 消费台账（`/var/lib/kylin-privhelper/approval-ledger`，目录 0700 / 日志 0600），每条记录 fsync 落盘后才执行命令，因此助手重启后同一令牌仍会被拒（`internal/privops/replayguard.go`）。台账按「令牌到期 + 10 分钟」的保留窗口压缩；台账不可用时执行 fail-closed 拒绝。

### 4.5 mTLS 设备证书闭环

```text
管理员发放短期 bootstrap token
  → Agent 生成私钥+CSR → EnrollNode(:9091, 仅注册面)
  → 平台 CA 签发节点证书(绑定 node_id/hostname/machine_id/版本)
  → 之后全部走 control 面(:9090) mTLS：
      TLS peer 证书抽取 SAN 的 kylin://node/<org>/<node_id>（无 SAN 的存量证书回退 CN/O 并告警）
        → 与请求体/DB 强一致校验
      CRL + DB cert_status 双重吊销校验
  → 支持：证书轮换 / 单证书吊销(即时断流) / CA 轮换(grace 重叠期)
         / re-issue 审批流(一次性 reissue token)
```

证书签名采用标准 X.509/TLS 栈。节点身份优先取自证书 **subjectAltName 的 URI 项 `kylin://node/<organization_id>/<node_id>`**；SAN 与 Subject DN 冲突时以 SAN 为准，一张证书包含多个平台身份时直接拒绝。注册面（:9091）要求配置 `KYLIN_ENROLL_CA_FILE`（固定 CA）或 `KYLIN_ENROLL_CA_SHA256`（指纹钉扎）；演示环境采用 TOFU 时必须显式设置 `KYLIN_ENROLL_INSECURE_TOFU=true` 并输出安全告警（见部署文档 6.3.1）。兼容证书可按 Subject DN 的 CN/O 完成身份校验并记录告警。

### 4.6 最小权限执行

核心设计是 ADR-002 的**特权分离**：不再让守护进程"临时变成 root"，而是让 root 能力住在另一个只会做固定几件事的进程里。

| 机制 | 实现 |
|---|---|
| 受限账户 | 守护进程以专用非 root 账户运行（`kylin-node-executor.service`，`NoNewPrivileges=true`、`ProtectSystem=full`、`ProtectKernelTunables/Modules`、`RestrictSUIDSGID`、`LockPersonality`） |
| 需 root 即硬拒 | `service.go` 在执行前检查 `needsRoot`，命中则**在 Agent 进程内直接拒绝**并提示须经特权助手；部署不使用 `sudoers` / `sudo -n`，Go 代码不调用 `sudo` |
| 特权下沉 | 写操作经 unix socket 交给 `kylin-privhelper`：`SO_PEERCRED` 校验对端 uid（且启动时拒绝把 uid 0 当作合法对端）、socket 属主 root、权限 0660、单连接 60 s 期限、请求体 1 MiB 上限；助手不可达时**fail-closed，绝不回落到本地执行** |
| 固定操作映射表 | 12 条封闭映射（6 个 service 动作 + 4 个 firewall 动作 + 2 个 cleanup 动作）。表外工具一律拒绝 |
| argv 由特权侧组装 | 守护进程**只传工具名与参数 JSON**，命令行由助手自己拼装。封禁 IP 的 rich rule 由助手构造，并额外拒绝回环 / 未指定 / 组播 / 链路本地地址——这类语义约束是 sudoers 表达不了的 |
| 策略文件防篡改 | `/etc/kylin-privhelper/allow.conf` 与 `approval.pub` 必须 root 属主且组/其他不可写，否则**启动即失败**；未知配置键、空白名单同样启动即失败（不静默忽略） |
| 助手侧限流 | 滑动 1 分钟窗口的 `max_ops_per_minute`（默认 30），在特权侧而非调用侧强制 |
| 无 shell | 命令以 argv 数组直接 `exec.CommandContext`，**全链路无 shell 解释器**，杜绝注入拼接 |
| 参数净化 | 服务名 / 包名正则 + allowlist；路径 `filepath.Clean` → 必须绝对路径 → allowedRoots 前缀匹配；IP 走 `net.ParseIP`；时长与整型有上下界 |
| 超时与截断 | 守护进程侧单命令默认 20 s、输出截断 64 KiB；助手侧默认 30 s |
| 资源锁与并发 | READ_SHARED / WRITE_EXCLUSIVE 资源锁由节点调度器持有；写工具 `maxConcurrency:1`；R5 禁止下发 |
| 备份与校验式回滚 | 清理前逐文件记录 mode / mtime / uid / gid / SM3 并归档副本（`files/` 目录 0700 root-only，元数据文件 rollback.json 为 0644 以便非 root 侧独立核对）；回滚时逐文件恢复并**重算 SM3 比对**，不符即返回 `RESTORE_VERIFY_FAILED` |
| 清理目录白名单 | `cleanupcore.ResolveTarget` 做**精确匹配**而非前缀匹配（`/tmp/aiops-demo-logs-evil`、`/var/log/aiops-demo/nested` 都会被拒）。清单来自 root 属主的 `/etc/kylin-privhelper/cleanup.conf`（`cleanup_allowed_dirs`），默认 `/var/log/aiops-demo` 与 `/tmp/aiops-demo-logs`；文件缺失/非 root 属主/权限过宽/内容非法一律 **fail-closed 回退到这两个默认目录**，绝不放开。配置里的每个目录还要再过硬禁清单：系统根基与一级目录（`/`、`/etc`、`/var`、`/var/log`、`/opt`…）拒绝，审计与数据库子树（`/var/log/audit`、`/var/lib/mysql`…）连同其**上级**一并拒绝 |
| 清理文件分类与保护名单 | `cleanupcore/classify.go`：按文件名模式 + 扩展名 + mtime 把文件分成 临时缓存 / 过期日志（含已轮转）/ 可清理文件 / 关键保护 / 活动日志 / 近期日志，**默认保留**——认不出来的一律不清理。保护判定优先级最高：数据库文件（`*.db`/`*.sqlite`/`*.ibd`…）、业务配置（`*.conf`/`*.yaml`/`*.json`…）、凭据（`*.pem`/`*.key`/`*.jks`…）、运行时状态（`*.pid`/`*.sock`/`*.lock`）、审计与登录证据（`audit.log*`/`wtmp*`/`btmp*`），以及文件名含 `mysql`/`postgres`/`redis`/`audit` 等组件标识的文件（拦住 `mysql-slow.log` 这类扩展名普通的数据库日志）。每个文件都带 `category`/`decision`/`rule`/`reason` 可逐条复核。**分类在 privhelper 侧（root）重跑**，plan 的结论不被信任 |
| 保护名单只能收紧 | `cleanup_protect_extra` 只往内置保护清单**追加**通配符；没有任何配置项能移除内置模式。阈值（日志保留天数、陈旧文件天数、活动日志窗口）越界或写成 0 时回退到默认值而不是取边界值，避免一次笔误把保留期整个抹掉 |

### 4.7 Kylin Native Guard 姿态联动（麒麟原生安全适配）

探测四项：KYSEC（读 `/sys/kernel/security/kysec/status` 等，兜底读 LSM 列表）、SELinux（读 `/sys/fs/selinux/enforce`，兜底 `getenforce`）、auditd（`systemctl is-active`，兜底查 `auditctl` 是否存在）、security-switch（读三处配置文件，兜底 `security-switch status`）。四项聚合为 `healthy / warning / critical / unsupported`，随 15 秒心跳上报并带采集时间戳。

| 场景 | 联动策略（fail-closed） |
|---|---|
| 控制面：R3+ 且姿态非 FRESH（含从未上报 / 过期） | `NATIVE_GUARD_*` 拒绝——不可验证则不放行 |
| 控制面：R3+ 且姿态 CRITICAL | `NATIVE_GUARD_CRITICAL` 拒绝 |
| 节点侧：R3/R4 且 KYSEC / auditd / security-switch 任一 critical | 本地护栏独立复判后拒绝 |
| 策略侧：auditd 异常 / KYSEC 关闭 / security-switch off | 分别触发升险到 R3 / 强审批 R4 / R3 以上默认拒绝 |
| 姿态采集失败 | 节点上报空状态，控制面按 UNKNOWN 处理并 fail-closed 拒绝 R3+ |

两点设计细节：① **SELinux 处于 disabled 时报告为"不支持"而非"危急"**，避免把以 KYSEC 为主的麒麟主机误判成不安全；② `kylin.security.*_status` 四个工具**自我豁免**姿态门禁——否则姿态一旦劣化就再也查不出它为什么劣化。

## 5. 审计与可观测设计

### 5.1 事件溯源与 SM3 哈希链

执行链路的事件覆盖以下五个环节。

| 执行环节 | 对应事件类型 |
|---|---|
| 接收指令 | `RUN_CREATED` / `RUN_STARTED` / `RUN_WAKEUP` |
| 感知环境 | `TOOL_INVOCATION_QUEUED` / `TOOL_INVOCATION_SUCCEEDED`（只读工具）、`CONTEXT_COMPILED` / `CONTEXT_SUMMARIZED` |
| 推理决策 | `MODEL_INVOCATION_STARTED` / `MODEL_INVOCATION_COMPLETED` / `MODEL_INVOCATION_FAILED`、`SUB_AGENT_*`（子 Agent 招募与交接） |
| 安全校验 | 门禁具名拒绝码（`POLICY_DENIED` / `R5_FORBIDDEN` / `PLAN_MODE_FORBIDS_WRITE` / `GRANT_EXCLUDES_*` / `ABAC_DENIED` / `ABAC_DENIED_HOST` / `NATIVE_GUARD_*`）、`APPROVAL_CREATED` / `APPROVAL_DECIDED` / `APPROVAL_AUTO_GRANTED` / `APPROVAL_REJECTED` / `APPROVAL_EXPIRED` / `APPROVAL_BINDING_MISMATCH` / `APPROVAL_ALREADY_CONSUMED` |
| 执行结果 | `NODE_INVOCATION_ACKNOWLEDGED` / `TOOL_INVOCATION_SUCCEEDED` / `TOOL_INVOCATION_FAILED` / `NODE_TOOL_FAILED`、`RUN_COMPLETED` / `RUN_FAILED` / `RUN_CANCELLED` / `BUDGET_EXCEEDED` / `WRITE_BUDGET_EXCEEDED` / `STAGNATED` |

```text
event_hash = SM3( prev_hash ‖ 规范化载荷 )      ← 控制面单条链，按 (run_id, sequence_no) 严格有序
```

主要相关表：

| 表 | 职责 |
|---|---|
| `agent_run_event` | 哈希链主表：event_id / sequence_no / event_type / actor / payload_json / prev_hash / event_hash；`hash_algorithm` 有 CHECK 约束锁定为 `SM3`；`(run_id, sequence_no)` 唯一 |
| `tool_invocation` | 工具调用记录（工具 id、版本、参数摘要、目标节点、风险、状态） |
| `execution_attempt` | 执行尝试（与审批令牌的 `execution_attempt_id` 一一对应，是"批准的那一次"的锚点） |
| `approval` | 审批单：决策、绑定字段、过期时间、决策人 |
| `agent_run_checkpoint` | 轮次检查点（run_id 主键，覆盖更新，终态删除） |
| `context_frame` | 上下文帧（消息历史重建的来源） |
| `app_audit_entry` | 平台侧 API 操作审计（登录、配置变更、审批决策等），与运行事件链正交 |

审计留存可审计推理摘要（用户意图 / 上下文编译结果 / 模型调用元数据 / 工具参数摘要 / 风险命中 / 审批状态 / 执行结果），不保存模型私有完整思维链。

**在线校验**：`GET /api/v2/agent-runtime/runs/{runId}/chain` 逐条重算并返回 `{valid, eventCount, brokenEventId, reason}`；任务时间线页把结论直接渲染成一枚标签，链完整显示为 ok 色，断链显示断点位置。

### 5.2 全链路 Trace 与指标

- **Trace**：W3C traceparent 由控制面产生，随 `SubmitInvocation` 透传到节点；节点在 `host.local_guardrail.check` / `host.mcp.tools_call` / `host.privhelper.call` 三处建立 span。按部署文档配置 OTel Java Agent，并接入 OTel Collector(4317/4318) → Tempo(3200) → Grafana(3001) 后，可检索跨进程链路；
- **指标**：后端经 micrometer 暴露 `/actuator/prometheus`；节点暴露 `/metrics`(:19100)，前缀 `kylin_node_executor_*`；Prometheus(9092) 采集，Grafana(3001) 预置面板；
- **搜索副本**：Elasticsearch(9200) 为**可选**组件（`AUDIT_ELASTICSEARCH_ENABLED` 默认 false）；**数据库为唯一可信源**，ES 仅做检索/聚合。

### 7.2 gRPC 接口（`NodeExecutorControlService`，3 方法；protobuf v2）

| 方法 | 类型 | 端口 | 说明 |
|---|---|---|---|
| `EnrollNode` | Unary | 9091（注册面，bootstrap token） | CSR 换发设备证书 |
| `ControlStream` | 双向流 | 9090（mTLS） | 主链路，见下表 |
| `ArtifactStream` | Client streaming | 9090（mTLS） | 产物/工件上传 |

`ControlStream` 消息面：

| 方向 | 消息 | 说明 |
|---|---|---|
| 下行 | `SubmitInvocation` | 受控调用：租户/run/实例/调用/尝试 id、工具 id 与版本、规范化参数与 `arguments_sm3`、风险码、执行模式、只读标记、锁版本、资源锁、`ApprovalToken`、deadline、traceparent |
| 下行 | `CancelInvocation` / `ReconcileInvocations` | 取消；重连后对账 |
| 上行 | `NodeCapabilities` / `NodeHeartbeat` | 首帧能力上报；15 秒心跳（携带 Native Guard 姿态与观测时间） |
| 上行 | `InvocationAck` | `RECEIVED` / `DUPLICATE`（幂等去重） |
| 上行 | `InvocationResult` / `ReconcileResult` | 执行结果；对账结果 |

协议自检：每帧带 `protocol_version` 与单调 `sequence`；版本不符直接中断流，序号为 0 或不大于上一条则作为重放/重复丢弃。节点收到 `SubmitInvocation` 后还会独立复算 `SM3(规范化参数) == arguments_sm3`、校验 deadline 未过期、R3/R4 必须带令牌、写操作必须带写排他锁——**任一不符在进入调度器之前就拒收**。
